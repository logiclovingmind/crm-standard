# CLAUDE.md — Logic Loving Mind OS (IZI Tier)

## What this project is

The Logic Loving Mind OS for Indian SMB brokerages (5–20 agents), sold as the **IZI tier** of Logic Loving Mind's product line. Never call it a CRM in anything a client reads — it is the OS. It is the destination system for leads generated by our WhatsApp AI bot (the core product — present in every tier). One deployment per client, each on its own small VPS.

**Design philosophy:** boring, reliable, cheap to run. One server, one process, one SQLite file. No Docker, no Kubernetes, no microservices. If a decision adds operational complexity, reject it.

## Deployment target

- **Host:** DigitalOcean Basic Droplet, **BLR1 (Bangalore)** region — "data stays in India" is a sales talking point, never move data out of region
- **Size:** $6/mo (1 vCPU, 1GB RAM, 25GB SSD). Everything must run comfortably in 1GB RAM. Upgrade path: one-click resize to 2GB ($12) if a client grows
- **OS:** Ubuntu 24.04 LTS
- **One droplet = one client.** No multi-tenancy in the app. Tenant isolation is at the infra level
- Client pays infra passthrough (~₹550–1,500/month)

## Tech stack (fixed — do not substitute)

| Layer | Choice | Notes |
|---|---|---|
| Runtime | Node.js 22 LTS | Single process via systemd |
| Backend | Express | REST API, JSON only |
| Database | SQLite via `better-sqlite3` | WAL mode ON. Fine up to ~50 concurrent users |
| Frontend | React + Vite | Built to static files, served by the reverse proxy |
| Reverse proxy | Caddy | Automatic HTTPS/Let's Encrypt, zero-config renewal |
| Auth | Session cookies (`express-session` + SQLite session store) | No JWT, no OAuth for login |
| Process mgmt | systemd unit | Restart on failure. No PM2 |
| Server hardening | ufw + fail2ban | fail2ban jail on the login endpoint via Caddy logs |

**Why SQLite:** one file to back up, zero DB administration, more than enough for 20 agents. Never suggest Postgres for this tier.

## Security requirements (non-negotiable)

- HTTPS everywhere; HTTP → HTTPS redirect at Caddy
- Passwords: bcrypt (cost 12), minimum 10 chars enforced at creation
- **Rate limiting on `/api/auth/login`:** 5 attempts / 15 min per IP (express-rate-limit) + fail2ban ban at 10 failures
- Session cookies: `httpOnly`, `secure`, `sameSite=lax`, 12-hour expiry
- All queries parameterized (better-sqlite3 prepared statements only — never string-build SQL)
- CSRF protection on all mutating routes
- No secrets in the repo. All config via `/etc/crm/.env`, loaded with dotenv

## Roles & access (enforce on API, not just UI)

| Role | Can see | Can do |
|---|---|---|
| `owner` | Everything | Everything + Excel export + user management + settings |
| `manager` | All leads, all agents | Assign/reassign leads, edit inventory, view dashboard |
| `agent` | **Only leads assigned to them** | Update own leads, add notes, schedule site visits |

Every lead-fetching query for an agent role must include `WHERE assigned_to = ?`. Write a middleware (`requireRole`, `scopeLeadsToUser`) and use it on every route — no per-route ad-hoc checks.

## Core features

### 1. Lead management
- **Pipeline statuses (fixed enum):** `New → Contacted → Site Visit → Negotiation → Closed / Lost`
- **Source tracking (enum):** `whatsapp`, `walk-in`, `99acres`, `magicbricks`, `referral`, `other`
- Status changes are logged to a `lead_activity` table (who, when, from → to) — this feeds follow-up logic
- Notes: free-text, timestamped, author-attributed, append-only

### 2. WhatsApp bot integration (the reason this OS exists)
- Inbound endpoint: `POST /api/integrations/whatsapp/lead`
- Auth: static bearer token per deployment (in `.env`), NOT session auth
- Payload contract (bot side already produces this):

```json
{
  "name": "string",
  "phone": "+91XXXXXXXXXX",
  "source": "whatsapp",
  "requirement": "2BHK, Whitefield, budget 80L",
  "conversation_summary": "string",
  "site_visit_requested": true,
  "preferred_slot": "2026-07-15T11:00:00+05:30"
}
```

- Dedupe on phone number: if a lead with the same phone exists and isn't `Closed/Lost`, append activity to the existing lead instead of creating a duplicate
- Must respond in <500ms; do Calendar sync async after responding

### 3. Property / project inventory
- Projects → Units. Unit fields: identifier (e.g. "A-1203"), type (1/2/3 BHK, plot, villa), area sqft, price, status
- **Unit status enum:** `available`, `blocked`, `sold`
- Leads can be linked to units of interest (many-to-many)

### 4. Site visit scheduling + Google Calendar sync
- Site visits have: lead, agent, datetime, project/unit, status (`scheduled`, `completed`, `no-show`, `cancelled`)
- Sync to a **single Google Calendar per deployment** (service account, calendar shared with client's Google account)
- Sync is one-way (CRM → Calendar) and fire-and-forget with retry (3 attempts, exponential backoff). A Calendar failure must never fail the OS operation — log and move on
- Store the Google `event_id` on the visit row so updates/cancellations sync

### 5. Follow-up nudges
- "No contact in 3 days" list: leads in `New`, `Contacted`, or `Site Visit` whose latest activity is >72h old
- Computed via query, not a background job. Shown as a badge/list on dashboard and per-agent view
- Agents see only their own stale leads; owner/manager see all

### 6. Dashboard (keep it basic)
- Leads this month (count + vs last month)
- Source breakdown (pie/bar)
- Conversion funnel (count per pipeline stage)
- Stale-lead count
- No date-range pickers, no custom reports in this tier

### 7. Search, filters, export
- Search: name / phone (partial match)
- Filters: status, source, assigned agent, date range
- **Excel export: owner role only.** Use `exceljs`, stream to response, all leads + notes summary. Log every export to `audit_log`

### 8. Language toggle — English / Kannada (ಕನ್ನಡ)
- All UI strings via an i18n layer (`react-i18next`), keys in `locales/en.json` and `locales/kn.json`
- Toggle persisted per user in their profile
- **Never hardcode UI strings in components.** Every new string goes into both locale files (English first; mark Kannada with `"__TODO__"` prefix if translation pending so it's greppable)
- Data (lead names, notes) is stored as entered — i18n applies to UI chrome only
- Fonts: ensure Kannada renders correctly (Noto Sans Kannada as fallback in the font stack)

### 9. Backups
- **Weekly** cron job (Sunday 02:00 IST): `sqlite3 crm.db ".backup"` → gzip → encrypt with `age` (key in `.env`) → upload to DigitalOcean Spaces (BLR1)
- Retention: **30 days**, prune older automatically
- Backup script must verify the backup opens (`PRAGMA integrity_check` on the copy) before uploading
- Log success/failure to a file; failure should be visible on the owner dashboard as a warning banner

## Database schema (starting point)

Tables: `users`, `sessions`, `leads`, `lead_activity`, `lead_notes`, `projects`, `units`, `lead_units`, `site_visits`, `audit_log`, `settings`.

Conventions:
- `id INTEGER PRIMARY KEY`, `created_at` / `updated_at` as ISO-8601 TEXT in IST
- Phone stored normalized as `+91XXXXXXXXXX`
- Migrations: plain numbered SQL files in `/migrations`, applied by a tiny runner at startup (track in `schema_version` table). No ORM, no Prisma

## Operational conventions

- `deploy/setup.sh` must take a fresh Ubuntu droplet to a running OS in one run (idempotent): create user, ufw, fail2ban, Node, Caddy, systemd, first admin account
- Support model: **best-effort, business hours, 24–48 hr response.** Do not build alerting infra beyond the backup-failure banner
- Keep total RSS under ~400MB so the 1GB droplet has headroom
- Uptime target is best-effort — no HA, no load balancing, ever, in this tier

## Development commands

```bash
npm run dev          # concurrently: server (nodemon) + client (vite)
npm run build        # vite build → client/dist
npm run migrate      # apply pending migrations
npm run seed:demo    # demo brokerage data for sales demos
npm test             # vitest — cover role scoping + WhatsApp intake dedupe at minimum
```

## What NOT to do

- No Postgres/MySQL, no Redis, no Docker, no queues, no websockets
- No multi-tenancy logic in code
- No OAuth login, no magic links
- No feature belongs here if it's an EON-tier feature (custom reports, multi-branch, audit dashboards, SLA monitoring)
- Do not add dependencies casually — every MB of RAM matters on a 1GB box
